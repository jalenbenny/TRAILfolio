Abstract

Machine learning models trained on routinely collected structured prehospital EMS records to predict stroke and severe stroke before hospital arrival. Performance is benchmarked against existing prehospital stroke assessment to assess its value for triage and routing decisions. Published in Scientific Reports (2026). This repository holds the modeling pipeline and evaluation code needed to reproduce the paper’s results.

Methods Summary

  • Data: structured EMS encounter records linked to ED/hospital outcomes, with geocoded census block group Area Deprivation Index (ADI) and dispatch (nature-of-call, priority) codes. See src/data/preprocessing.py.
  • Tasks: two binary labels, stroke (any stroke vs. no stroke) and severe (severe stroke vs. non-severe/no stroke).
  • Cohorts: full cohort; EMS-suspected (CPSS performed); stroke-relevant (stroke and stroke mimics). A sensitivity analysis drops dispatch variables (_nodisp).
  • Models: random forest, XGBoost, and a shallow neural network, each tuned with Optuna (5-fold cross-validated ROC-AUC on the combined training and validation data) and evaluated on a stratified held-out test set (n = 2,466 full; 375 EMS-suspected; 772 stroke-relevant). Probabilities are calibrated post hoc: k-fold calibration for the tree models, attended temperature scaling for the neural network.
  • Evaluation: ROC-AUC and PR-AUC with confidence intervals, calibration, sensitivity/specificity operating-point trade-offs, confusion matrices, comparison against EMS CPSS and dispatch identification, and SHAP feature importance. A sub-analysis (src/scripts/ed_measures_analysis.py) examines ED NIHSS measures.

Data Availability

This project uses identifiable clinical data: prehospital EMS electronic patient care records (ZOLL RCSQL database extracts) linked to emergency department outcomes, and, for the ED measures sub-analysis, EHR flowsheet data. The data contain PHI, are held on the institution’s secure research share under IRB approval, and are not shared. Nothing patient-identifiable is in this repository: data/raw/ is empty and gitignored.

The repository contains code, configuration, tuned hyperparameters, figures, and the held-out-set evaluation bundles (labels and predicted probabilities, with no identifiers) used to produce the paper’s figures and tables. The public ADI values come from the Neighborhood Atlas.

For data access questions, contact msaban@luc.edu.

How to Reproduce

# setup
conda-lock install -n stroketriage-env conda-lock.yml   # or: conda env create -f environment.yml
conda activate stroketriage-env                         #     or: pip install -r requirements.txt
pip install -e .

# run
python src/main.py --list
python src/main.py analysis

Detailed steps follow.

Prerequisites

You must have Anaconda or Miniconda installed on your system to manage the Python environment and its dependencies.

Installation and Setup

  1. Clone the Repository

    git clone https://github.com/TootooniLab/stroke-triage-ml.git
cd stroke-triage-ml

  2. Create and Activate the Conda Environment

    Use the conda-lock.yml file to create a new Conda environment that contains all necessary packages. This command will create an environment named stroketriage-env.

    conda-lock install -n stroketriage-env conda-lock.yml
conda activate stroketriage-env

    (Alternatively, you can use environment.yml: conda env create -f environment.yml, or pip install -r requirements.txt in a Python 3.12 environment.)

    Important: After activating the environment, you must set the PYTHONHASHSEED environment variable to ensure reproducibility.

    conda env config vars set PYTHONHASHSEED=0
conda deactivate
conda activate stroketriage-env

  3. Install the Project in Editable Mode

    This step makes the src folder recognizable as a Python package, so all scripts and notebooks can use absolute imports (e.g., from config.config import ...) without any further setup.

    From the root directory of the project, run:

    pip install -e .

    (The -e stands for “editable,” meaning you can change the source code without needing to reinstall the package.)

  4. Configure Data Paths

    Open the src/config.yml file in a text editor. You must modify the directory paths to point to the location of your datasets.

    Update the following keys:

    • split_dir: Path to your directory containing data splits (train, validation, test sets).
    • data_dir: Path to your directory containing the raw data files.
    • ph2: Path to the main dataset file.
    • geo: Path to the file containing census codes for addresses.
    • adi: Path to the file containing Area Deprivation Index (ADI) values.
    • fdc_desc, noc, prior: Paths to tables from the SQL database (referencing ZOLL Data Systems RCSQL Data Dictionary).
    • flowsheet_data_path: Path to the ED flowsheet data (ED measures sub-analysis only).

    Note: This codebase is designed for the specific datasets used in our publication. The fdc_desc, noc, and prior files correspond to specific SQL tables. While the code provides a framework for analysis, using it with different prehospital data may require modifications to account for schema differences. This repository is primarily intended for reproducibility of the published results.

    Example:

    # Directory for data splits.
split_dir: "C:/Users/YourName/Documents/StrokeData/DataSplits/"
# Directory for raw data.
data_dir: "C:/Users/YourName/Documents/StrokeData/Raw/"

Running the Analysis

Once the setup is complete, you can run the analysis pipelines through the entry point:

python src/main.py --list          # list available pipelines
python src/main.py analysis        # full training, evaluation, tables and figures
python src/main.py ed-measures     # ED measures (NIHSS performance) sub-analysis

These dispatch to the scripts in src/scripts/, which can also be run directly:

python src/scripts/run_analysis.py
python src/scripts/ed_measures_analysis.py

By default (retune_models: false, retrain_models: true in src/config.yml) models are retrained from the saved Optuna parameters in results/tuning/ rather than re-tuned. Because the project is installed as a package, you can also directly run any other script or work interactively in a notebook, and all imports will resolve correctly.

Project Structure

  • src/: All Python source code.
    • main.py: Entry point (python src/main.py --list).
    • config.yml: Project configuration (data paths, cohort, task, tuning flags, output directories).
    • config/: Configuration loading and path management.
    • data/: Data loading and preprocessing.
    • models/: Model training, tuning, and calibration logic.
    • evaluation/: Model performance evaluation and figure/table generation.
    • pipelines/: Training pipeline and preliminary/descriptive analysis.
    • scripts/: Executable analysis scripts (run_analysis.py, ed_measures_analysis.py).
  • results/: Generated outputs (see results/README.md).
    • figures/: Generated plots and figures (figure_dir).
    • metrics/: Model evaluation results and tables (output_dir).
    • tuning/: Optuna best hyperparameters (model_dir).
  • data/: raw/ is gitignored and never committed; processed/ is for synthetic or de-identified samples only.
  • docs/, notebooks/: Supporting documentation and exploratory work.
  • conda-lock.yml: Lock file for exact environment reproduction.
  • environment.yml, requirements.txt: Conda environment file and pip requirements.
  • setup.py: Makes the project installable as a Python package.
